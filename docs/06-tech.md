# Технічна архітектура

## 27. SEO-архітектура

- Всі контентні сторінки — SSG: повний HTML без клієнтського рендерингу.
- Унікальні title/description за шаблонами:
  - Продукт: `{Назва} — {категорія в однині} | {Бренд}`; description — з рядка призначення.
  - Категорія: `{Категорія}: {N} моделей | {Бренд}`.
- OpenGraph з продуктовим фото; canonical: сторінки з фільтр-параметрами канонікалять на чисту категорію.
- **Фільтрові URL не індексуються** (`noindex,follow` + відсутні в sitemap) — контроль crawl budget, жодної безконтрольної генерації сторінок фільтрів.
- Structured data (JSON-LD): `Organization`, `BreadcrumbList`, `Product` з `offers` (ціни публічні — рішення Q3; `availability` мапиться на статуси schema.org), `ItemList` на категоріях.
- `sitemap.xml` генерується на збірці; `robots.txt` закриває `/compare`, `/request`, wizard і query-параметри.
- 404 зі схожими продуктами; зміна slug → 301 (мапа редиректів у репозиторії).
- Мова MVP — `uk`; hreflang з'явиться разом з EN-версією (V2).

## 28. Публічна архітектура даних і API

Ключове рішення — **static-first: публічного live-API читання каталогу немає взагалі**.

```
ЕТАП 1 (старт, рішення Q2): продукти ведуться програмно —
  контент-файли в репозиторії за схемою PublicProduct DTO (валідація на збірці)
ЕТАП 2 (пізніше, рішення Q5): самописна ERP віддає ту саму проекцію через експорт/API
   │
   │  на обох етапах — той самий whitelist-мапер (публічна проекція; deny-by-default)
   ▼
products.public.json  + зображення (EXIF стерто) + документи (public-позначені)
   + контент-шар: рішення, синоніми, відгуки (окремий редакційний контур — 04-logic §22)
   │
   │  збірка сайту в CI: SSG сторінок + пошуковий індекс + JSON категорій
   ▼
CDN ──► користувач (HTML + статичні JSON)

Єдиний динамічний ендпоінт:
POST /api/requests ──► CRM/ERP (Lead / ClientRequest) + резервне сповіщення менеджерів
```

**Чому так:**
- Мінімальна поверхня атаки: назовні не стирчить жодного read-ендпоінта до ERP.
- Data exposure review зводиться до ревью одного експорт-файлу, а не поведінки API.
- Максимальна швидкість і стійкість на слабкій мережі; дешевий і стійкий до DDoS хостинг (CDN).

**Оновлення каталогу:** webhook з ERP → перезбірка (хвилини) або розклад кожні N годин. Якщо знадобиться частіша актуальність наявності — крихітний `GET /api/availability` (slug → один із 4 публічних статусів), V2.

### Public Product DTO (повний перелік полів; решта — заборонена за замовчуванням)

```
PublicProduct {
  slug, name, shortDescription,
  category: { slug, name },
  useCases: ["vehicle", …],
  badges: ["Посилена батарея", …],
  publicImages: [{ src, alt, width, height }],
  keySpecs: [{ label, value }],                  // 4–6 для картки і фолда
  publicSpecifications: [                        // згруповані ТТХ
    { group: "Радіочастотні характеристики", items: [{ label, value }] }, …
  ],
  configuration?: {
    optionGroups: […], variants: [{ options, sku, price, availability }],
    defaultVariantId
  },
  publicPrice: { from, currency } | { type: "on_request" },
  availability: "in_stock" | "production_3_5d" | "on_order" | "temporarily_unavailable" | "check_with_manager",
  documents: [{ title, type, url, sizeBytes }],
  packageContents: [string],
  warrantyMonths,
  relatedSlugs: […],
  compatibility: [{ slug, relation: "works_with" | "requires" | "recommended_addon", note? }],
  reviews: [PublicReview]      // з контент-шару, НЕ з ERP — модель і правила: 04-logic §22
}
```

`POST /api/requests` приймає payload з [04-logic.md](04-logic.md) §21: валідація, rate limit, honeypot, черга з ретраєм у CRM.

## 29. ERP-дані: що МОЖНА публікувати

| Дані | Умова публікації |
|---|---|
| Назва, публічний опис, категорія | після контент-ревью |
| Публічні ТТХ | лише whitelist-ключі, погоджені продуктовим і безпековим ревью |
| Роздрібна ціна («від») | так — рішення власника (Q3, 2026-08-12): ціни публічні; «від X грн» для конфігурованих, точна для фіксованих SKU; `Ціна за запитом` лишається опцією для окремих позицій |
| Наявність | **тільки** як один із 4 публічних статусів (мапінг нижче); ніколи — точні залишки |
| SKU варіантів | так — потрібен для комунікації з менеджером; ніколи як назва |
| Фото | після ревью + автоматичний strip EXIF/гео-метаданих на збірці |
| Документи | лише з позначкою `public` у сховищі |
| Гарантія, комплектація | так |

### Мапінг наявності ERP → публічний статус

```
залишок ≥ порогу відображення     → «В наявності»
0, виробнича черга ≤ 5 днів       → «Виробництво 3–5 днів»
0, виробляється під запит          → «Під замовлення»
пауза виробництва / знято          → «Тимчасово недоступний»
дані ненадійні / новий продукт     → «Уточнюйте наявність»
```

Внутрішні статуси ERP назовні не показуються ніколи.

## 30. ERP-дані: що публікувати ЗАБОРОНЕНО

- Собівартість, закупівельні ціни, маржа.
- BOM, виробничі специфікації та інструкції.
- Постачальники та комплектуючі.
- Серійні номери.
- **Точні складські залишки й обороти** — обсяги виробництва оборонної продукції є чутливою інформацією.
- Ціни/умови конкретних юросіб; будь-які клієнтські дані.
- **Будь-яка інформація про покупців** (хто, що і скільки купив) — воєнно-чутлива.
- Внутрішні статуси ERP, нотатки менеджерів.
- Чернетки продуктів (draft / неопубліковане).
- Адреси складів і виробництва; імена співробітників.

### Процес data exposure review (обов'язковий, повторюваний)

1. Експорт будується **whitelist-мапером**: поле потрапляє назовні, лише якщо явно перелічене в DTO. Нових полів «за замовчуванням» не існує.
2. Перед першим релізом і при кожній зміні DTO — ручне ревью експорт-файлу: продакт + відповідальний за безпеку.
3. Фото: автоматичний strip EXIF (гео, серійні номери камер) + ревью фону кадру (позиції, люди, шеврони, номери частин, документи на столі — не мають потрапляти в кадр).
4. Тексти: заборона згадок конкретних підрозділів і місць застосування без окремого дозволу.
5. CI-перевірка: **збірка падає**, якщо в експорті з'являється поле поза whitelist.
6. Контент користувачів (відгуки, фото, відео) — окремий обов'язковий OPSEC-чекліст перед публікацією: анонімізація підпису, блюр облич/шевронів/номерів, strip EXIF, без локацій і дат подій, зафіксована згода автора ([04-logic.md](04-logic.md) §22).

## 31. Компонентна архітектура frontend

> **Рішення власника (2026-08-12):** JS-фреймворк у стеку дозволений, навіть якщо навантажує систему; оптимізація продуктивності — окрема пізніша фаза. Бюджети [05-ux-quality.md](05-ux-quality.md) §26 стають цільовими орієнтирами фази оптимізації, а не блокерами розробки.

Рекомендація з урахуванням рішення: **Next.js (React) у режимі SSG** — повноцінний JS-стек; статична генерація сторінок каталогу зберігається (SEO, швидкий перший рендер, static-first архітектура §28 не змінюється), а інтерактив (пошук, фільтри, конфігуратор, порівняння, заявка) — звичайні React-компоненти. Astro + острови лишається запасним варіантом, якщо фаза оптимізації цього вимагатиме. У Q6 відкритим лишається: хто підтримує фронтенд і де хостимо.

```
src/
  layouts/     Base, Catalog
  components/
    layout/    Header, MobileNav, Footer, Breadcrumbs
    ui/        Button, Badge, Chip, Input, Select, CheckboxChip, RadioChip,
               Accordion, Tabs, Table, Modal, Drawer/BottomSheet,
               Skeleton, EmptyState, Alert, Toast
    catalog/   ProductCard, ProductGrid, CategoryCard, ActiveFilters,
               *SearchBox, *FilterPanel, *SortSelect
    product/   Gallery, KeySpecs, SpecGroups, PriceBlock, AvailabilityBadge,
               DocumentsList, PackageContents, RelatedProducts,
               *Configurator, *StickyCTA
    compare/   *CompareToggle, *CompareBar, *CompareTable
    solutions/ SolutionCard, RecommendationList, *Wizard (V2)
    request/   *RequestButton, *RequestDrawer, *RequestList
  data/        products.public.json, categories.json, solutions.json,
               filter-configs.json, search-index.json, synonyms.json
  pages/       маршрути з 02-concept-ia-flows.md §9

* — інтерактивні острови (гідруються); решта — статичний HTML без JS.
```

Стан і зберігання:
- **URL — джерело правди** для фільтрів, сортування, конфігурації, списку порівняння (шерабельність у месенджери).
- **localStorage:** список порівняння, список заявки, останні пошуки, чернетка форми.
- Жодного глобального state-менеджера: острови спілкуються через URL + custom events + localStorage.
