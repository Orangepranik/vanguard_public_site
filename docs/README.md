## Методологія

```
Цілі → Контекст та аудиторія → Концепція → Інформаційна архітектура
→ User Flow → Wireframe → UI-система → Реалізація
```

Документи впорядковані за цією ж логікою. Наступний етап після підтвердження документації:

```
Wireframes високої деталізації → UI-система → компонентна архітектура → імплементація
```

## Ключові проектні рішення (TL;DR)

1. **Дві рівноправні осі навігації** до одного пулу продуктів: «Каталог» (за типом) і «Рішення» (за задачею). Обидва шляхи сходяться на сторінці продукту.
2. **Людські назви конфігурацій** («4 діапазони, виносні антени») замість SKU. SKU лишається в техблоці, пошуку та заявці.
3. **Static-first архітектура:** весь каталог — статичний HTML з CDN. На старті продукти ведуться програмно в репозиторії за схемою PublicProduct DTO (рішення Q2); пізніше самописна ERP віддаватиме ту саму проекцію через API (Q5). Публічного live-API читання немає; єдиний динамічний ендпоінт — `POST /api/requests`.
4. **Заявка замість кошика на старті** («список заявки» на кілька позицій): клієнт залишає заявку, менеджер зв'язується і супроводжує оплату. Онлайн-оплата — пізніша ітерація (рішення власника, 2026-08-12).
5. **Mobile-first + слабка мережа** як базовий сценарій, не edge case: бюджети продуктивності жорсткі й перевіряються в CI.
6. **OPSEC вбудований у дизайн:** мінімум ПІІ у заявці, self-hosted аналітика, strip EXIF з фото, публічні статуси наявності замість точних залишків, data exposure review як процес.
7. **Реальний досвід як шар довіри:** відгуки користувачів з фото/відео та історії застосування на сторінках продуктів — публікація лише після двоетапної модерації з OPSEC-чеклістом ([04-logic.md](04-logic.md) §22).
8. **Сумісність продуктів:** типізовані зв'язки «Працює з…» на сторінках продуктів і у фільтрах аксесуарів.
