# Функціональна логіка

## 17. Пошук

### Що індексується

Назва + альтернативні написання (кирилиця / латиниця / жаргон) · SKU й артикули (зокрема старі) · категорія · теги задач · діапазони · ключові характеристики · короткий опис.

Приклади очікуваної поведінки з ТЗ:
- `авто` → продукти з тегом «автомобіль» + рішення «Для автомобіля»;
- `1G 3G 5G 6G` → детектор із відповідними діапазонами;
- `виносні антени` → конфігурації з виносними антенами.

### Словник синонімів (контентний файл, поповнюється з логів пошуку)

```
дрон = БПЛА = FPV = коптер = мавік
авто = автомобіль = машина = борт = пікап
виносні антени = зовнішні антени
кожан = kozhan = kojan
акум = батарея = АКБ = живлення
глушилка = РЕБ = придушення
```

### Механіка

Каталог — сотні позицій максимум, тому: повнотекстовий **індекс будується на етапі збірки** і вантажиться як статичний JSON (десятки КБ, кешується назавжди до перезбірки). Пошук виконується **на клієнті**: миттєвий відгук, нуль запитів до сервера, працює на слабкій мережі після першого завантаження.

- Fuzzy-збіг (1–2 помилки), префіксний збіг, транслітерація.
- Вага полів: назва > SKU > теги задач > характеристики > опис.

### UX пошуку

- Поле завжди відкрите на сторінках каталогу; в header — іконка, що розгортає поле (mobile — на всю ширину, автофокус).
- Підказки під час введення, згруповані: **Категорії · Рішення · Продукти**. Debounce 150 мс.
- Enter → сторінка результатів `/catalog?q=…` (сітка + фільтри для звуження).
- Останні запити — localStorage.

### Zero-result

«Нічого не знайдено за “…”» → перевірити написання · популярні категорії · **«Опишіть задачу — підберемо»** (веде у форму заявки з коментарем, куди підставлено запит). Кожен zero-result логується як метрика — джерело поповнення синонімів і контенту.

## 18. Фільтри

### Принципи

1. Набір фільтрів **залежить від категорії** — жодного універсального списку на 30 позицій.
2. Фільтри описуються **даними** (конфіг категорії), а не хардкодом у компонентах.
3. Тільки людські labels; мапінг внутрішніх кодів — у контент-шарі.

### Схема конфігурації

```
CategoryFilterConfig {
  categoryId: "detectors",
  filters: [
    { id:"bands",        label:"Діапазони",             type:"multi",
      options:[{value:"1g",label:"1G"}, {value:"3g",label:"3G"}, …] },
    { id:"bandsCount",   label:"Кількість діапазонів",  type:"single" },
    { id:"antennaType",  label:"Антени",                type:"single",
      options:[{value:"internal",label:"Вбудовані"},{value:"remote",label:"Виносні"}] },
    { id:"power",        label:"Живлення",              type:"multi" },
    { id:"formFactor",   label:"Спосіб використання",   type:"multi",
      options:[портативний · на автомобіль · стаціонарний] },
    { id:"price",        label:"Ціна",                  type:"range" },
    { id:"inStock",      label:"Лише в наявності",      type:"toggle" }
  ]
}
```

Для антен набір інший: Тип · Діапазон · Роз'єм · Монтаж · Ціна. Для РЕБ — свій (після безпекового ревью параметрів).

### Мапінг внутрішніх кодів → публічні labels (єдина таблиця)

| Внутрішнє | Публічне |
|---|---|
| 3S2P | Посилена батарея |
| STD | Стандартна батарея |
| EXT | Виносні антени |
| INT | Вбудовані антени |
| 4CH | 4 діапазони |

### Поведінка

- **Стан фільтрів у URL** (`?bands=1g,5g&antenna=remote`) — посилання шериться в месенджери; для цієї аудиторії це основний спосіб «порадитись із побратимами».
- Фасетні лічильники біля опцій; опції з нульовим результатом — disabled, а не приховані.
- Активні фільтри — chips над сіткою + «Скинути все».
- Фільтрація клієнтська по статичному JSON категорії → миттєва, без мережі.
- Mobile: bottom-sheet; групи згорнуті, крім двох перших; кнопка застосування з лічильником — **«Показати 8 моделей»**.

## 19. Конфігуратор

**Коли застосовується:** продукт має варіанти (діапазони, антени, батарея, виконання). Користувач обирає зрозумілі параметри — SKU варіанта система визначає сама.

### Модель даних

```
ConfigurableProduct {
  optionGroups: [
    { id:"bands",   label:"Діапазони", type:"single",
      options:[{id:"4b", label:"4 діапазони (1G/3G/5G/6G)", priceDelta:0}, …] },
    { id:"antenna", label:"Антени",    type:"single",
      options:[{id:"int", label:"Вбудовані", priceDelta:0},
               {id:"ext", label:"Виносні",  priceDelta:+3500}] },
    { id:"battery", label:"Батарея",   type:"single",
      options:[{id:"std", label:"Стандартна", priceDelta:0},
               {id:"rein",label:"Посилена",  priceDelta:+2400}] }
  ],
  variants: [   // ЛИШЕ допустимі комбінації
    { options:{bands:"4b", antenna:"ext", battery:"std"},
      sku:"KOJ-1G3G5G6G-EXT-STD", price:45500, availability:"in_stock" },
    …
  ],
  defaultVariantId   // рекомендована (найпопулярніша) комбінація
}
```

### Правила

- Показуються лише допустимі комбінації; недоступна опція — **disabled з поясненням** («Недоступно з вбудованими антенами»), а не прихована.
- Дефолт — рекомендована конфігурація: сторінка ніколи не відкривається «порожньою» і завжди має ціну.
- Кожна зміна миттєво оновлює: ціну, наявність, людський підсумок конфігурації.
- Ціни опцій — як дельти (`+2 400 грн`); підсумок — повна ціна.
- Конфігурація серіалізується в URL (`?cfg=4b-ext-std`) — можна переслати посилання на точну комплектацію.
- Обрана конфігурація повністю передається в заявку.

### Блок підсумку

```
Обрана конфігурація
4 діапазони · Виносні антени · Стандартна батарея
Артикул: KOJ-1G3G5G6G-EXT-STD        ← дрібно; корисно для розмови з менеджером
Ціна: 45 500 грн · ● В наявності
[Залишити заявку]
```

SKU показується дрібним допоміжним текстом — він потрібен для комунікації, але не є назвою конфігурації.

## 20. Порівняння

### Правила

- 2–4 продукти **однієї категорії** (інакше рядки ТТХ не збігаються). Спроба додати з іншої категорії → тост: «Порівнюються продукти однієї категорії. Почати нове порівняння?»
- Стан: localStorage (переживає перезавантаження) + ids в URL — `/compare?ids=kozhan-4,kozhan-4-pro` (шерабельно).
- Додавання: чекбокс на картці в сітці, кнопка «⇄ Порівняти» на сторінці продукту.
- Після першого доданого продукту — sticky-панель знизу: мініатюри + `[Порівняти N]` + очистити.

### Сторінка `/compare`

```
Sticky-шапка колонок: фото · назва · ціна · наявність · [Детальніше] · ×
Перемикач: [Усі параметри | Лише відмінності]
Рядки: Призначення · Ціна · Діапазони · Живлення · Вага · Тип антен · Гарантія · Наявність
       + повні групи ТТХ (ті самі групи, що на сторінці продукту)
Відмінні значення — виділені фоном
Mobile: 2 колонки поруч, 3–4 — горизонтальний скрол; шапка колонок sticky
CTA в кожній колонці: [Залишити заявку]
```

Стани: 0 продуктів — пояснення механіки + посилання в каталог; 1 продукт — «Додайте ще хоча б один для порівняння».

## 21. Заявка / кошик

> **Рішення власника (2026-08-12):** на старті всі продажі йдуть через заявку — клієнт заповнює форму, менеджер зв'язується та супроводжує угоду й оплату. Онлайн-оплата (автооплата) додається пізнішою ітерацією.

### Матриця моделей продажу

| Тип продукції | Приклади | Модель продажу | Чому |
|---|---|---|---|
| Конфігуровані системи | Детектори, РЕБ | **Заявка (RFQ)** | потрібні консультація, комплектація, рахунок для підрозділу/фонду, узгодження строків |
| Комплекти | Набори під сценарій | **Заявка** | так само |
| Прості товари | Антени, кабелі, АКБ, кріплення | старт: заявка · пізніше: кошик + онлайн-оплата | консультація не потрібна, але на старті один флоу; автооплата — коли будуть готові процеси |

Складна система і кабель не повинні продаватися одним UX — але в MVP уніфікуємо на заявці, бо вона покриває обидва випадки; кошик додається у V2 лише для категорії аксесуарів.

### Механіка MVP — «список заявки» (request list, не кошик)

- Будь-де: `[Залишити заявку]` → одразу форма з поточним продуктом і конфігурацією.
- Додатково: `[+ Додати до заявки]` накопичує кілька позицій (localStorage), потім одна форма на все. Це закриває сценарій фонду «беру детектор + 2 антени + АКБ» без e-commerce-механіки.
- Позиції показані над формою: продукт · конфігурація · кількість (можна змінити/видалити).

### Форма (drawer поверх поточної сторінки, без редіректу)

```
Ім'я*                    [___________]
Телефон*                 [+380 __ ___ __ __]     ← маска, inputmode=tel
Зручний спосіб зв'язку   ( ) Дзвінок  (●) Telegram  ( ) Signal  ( ) WhatsApp
Організація / підрозділ  [___________]           ← необов'язково — свідомо (OPSEC)
Коментар                 [___________]           ← необов'язково
[Надіслати заявку]
```

Мінімум обов'язкових полів: ім'я + телефон. Користувач **ніколи не описує продукт руками** — все підставляється автоматично.

### Payload

```
{
  items: [{ productId, slug, configuration:{…}, sku, qty, priceAtSubmit }],
  name, phone, contactChannel,
  organization?, comment?,
  sourcePage, utm?, submittedAt
}
```

### Backend-інтеграція

> **Рішення власника (2026-08-12, Q5):** ERP самописна, зв'язка — пізніше. На старті заявки в ERP не йдуть.

- **Старт:** `POST /api/requests` зберігає заявку в черзі на боці сайту (просте сховище) і сповіщає менеджерів (email + Telegram-бот). Заявка не губиться ніколи.
- **Пізніше:** самописна ERP підключається до тієї самої черги/вебхука і створює Lead/ClientRequest; контракт payload фіксується зараз — фронтенд при підключенні не змінюється.
- Канал сповіщень недоступний → ретрай із черги; користувачу однаково показується успіх.
- Антиспам: honeypot-поле + rate limit по IP + серверна валідація. **Без CAPTCHA** — це бар'єр для польових умов.

### Після відправлення

- Успіх: номер заявки + очікування («Менеджер зв'яжеться протягом робочого дня») + прямий телефон для термінових випадків.
- Помилка мережі: дані форми **не втрачаються**, кнопка «Спробувати ще раз», поруч телефон і месенджери як запасний канал.

## 22. Відгуки та досвід застосування (розширення за брифом власника)

**Мета:** відповісти на головне питання покупця — *«Чи можу я довіряти цьому обладнанню в реальній ситуації?»* Відгук тут — не текстова оцінка, а підтвердження роботи обладнання в реальних умовах.

### Формати

1. **Відгук** (блок на сторінці продукту): текст + фото/відео + контекст застосування (тип задачі: «на автомобілі», «стаціонарний пост») + підпис + опційна оцінка.
2. **Історія застосування** (курирований кейс; розділ `/cases` — V2): задача → умови → як спрацювало обладнання → результат (вчасно виявлена загроза; збережені люди, техніка чи позиції). Пише редакція за матеріалами користувача; текст погоджується з автором.

### Джерела

- **MVP:** відгуки збирають менеджери з реальної комунікації (месенджери, дзвінки) за явною згодою автора; публікація через контент-шар, не через ERP.
- **V2:** форма «Поділитися досвідом» на сторінці продукту (текст + медіа) → черга модерації.

### Модерація — двоетапна, без винятків

1. **Контентна:** відгук від реального користувача саме цього продукту; по суті; без образ.
2. **OPSEC** — правила анонімізації:
   - підпис — позивний або роль («оператор БПЛА», «боєць підрозділу Сил оборони»); ПІБ і номер частини — ніколи;
   - без локацій, дат конкретних подій, напрямків і назв операцій;
   - фото/відео: автоматичний strip EXIF; блюр облич, шевронів, номерних знаків і бортів техніки, впізнаваних орієнтирів; екрани приладів — лише якщо не розкривають налаштування/частоти;
   - дата публікації — з точністю до місяця («березень 2026»), без прив'язки до події;
   - зафіксована згода автора на публікацію (зберігається внутрішньо);
   - жодних коментарів і відповідей у реальному часі — це не соцмережа.

### Модель даних (контент-шар, НЕ ERP)

```
PublicReview {
  productSlug,
  displayName,          // позивний або роль
  roleLabel?,           // «оператор БПЛА»
  rating?,              // 1–5, опційно; агрегований рейтинг не показуємо, поки відгуків < 5
  text,
  media: [{ type: "photo" | "video", src, poster? }],
  useCaseTag?,          // «на автомобілі», «піхота»…
  publishedAt,          // точність — місяць
  verified: true        // публікуються лише перевірені
}
```

### Відображення

- **Сторінка продукту:** блок «Відгуки та досвід застосування» — 2–3 розгорнуті відгуки + [Показати всі] (розгортання на місці; окремої сторінки відгуків у MVP немає). Медіа — lazy; відео — лише по кліку з постером.
- **Головна:** 2–3 цитати з посиланнями на продукти.
- **Порожній стан:** «Збираємо відгуки користувачів цього продукту. Користуєтесь ним? Поділіться досвідом» + контакт.

## 23. Сумісність продуктів

Технічний ланцюжок вибору (бриф, п. 4) включає сумісність: інженер має бачити, з чим працює пристрій, без дзвінка менеджеру.

### Модель даних

```
compatibility: [
  { slug: "ant-5g",  relation: "works_with",        note: "через роз'єм SMA" },
  { slug: "akb-x",   relation: "recommended_addon", note: "подовжує роботу до N год" },
  { slug: "mount-a", relation: "requires" }
]
```

### Використання

- **Сторінка продукту:** блок «Працює з…» — картки сумісних продуктів із короткою приміткою.
- **Каталог аксесуарів:** фільтр «Сумісність із продуктом» будується з цих самих зв'язків (зворотний індекс на етапі збірки).
- Зв'язки двосторонні: додали антену до детектора → детектор автоматично з'являється на сторінці антени.
- Джерело: ERP, якщо зв'язки там ведуться (питання Q16); інакше — ручний контент-шар для стартового асортименту.
