# Концепція, інформаційна архітектура, user flows

## 7. Концепція каталогу

Ядро концепції — **дві рівноправні осі доступу до одного пулу продуктів**:

```
                     ПУЛ ПРОДУКТІВ (одна база, теги задач)
                        ▲                         ▲
         вісь «ТИП»     │                         │     вісь «ЗАДАЧА»
         /catalog       │                         │     /solutions + майстер
  «Я знаю, що шукаю»    │                         │  «Я знаю, навіщо мені»
  Каталог → Категорія → ПРОДУКТ ◄─── сходяться ───► Рішення → Рекомендації → ПРОДУКТ
```

- Продукт зберігається один раз і має теги сценаріїв використання; сторінки «Рішень» — курировані добірки за цими тегами.
- **Сценарій A** (знає продукт): Каталог → Детектори → «КОЖАН». ≤ 3 кліки.
- **Сценарій B** (знає задачу): Рішення → «Для автомобіля» → рекомендації → продукт. Або майстер підбору за 3–4 кроки.
- Обидва шляхи сходяться на одній і тій самій сторінці продукту — контент не дублюється.

Похідні рішення:
- **Конфігуровані продукти** — одна сторінка продукту + конфігуратор з людськими опціями; SKU генерується системою і не є назвою.
- **Модель продажу** — заявка (RFQ) як єдина на старті: після заявки з клієнтом зв'язується менеджер і супроводжує оплату (рішення власника). Онлайн-оплата — пізніша ітерація ([04-logic.md](04-logic.md), розділ 21).
- **Порівняння** — в межах однієї категорії, 2–4 продукти.
- Контент кожного продукту веде користувача ланцюжком *Що це? → Для чого? → Чи підійде мені? → Скільки коштує? → Як купити?*; технічний рівень (характеристики → комплектація → сумісність → документація → умови експлуатації → досвід користувачів) розкривається нижче за сторінкою.
- **Реальний досвід як шар довіри** — відгуки користувачів (текст, фото, відео) та історії застосування на сторінках продуктів; публікація лише після OPSEC-модерації ([04-logic.md](04-logic.md) §22).

## 8. Інформаційна архітектура

> ⚠️ Категорії нижче — гіпотеза на основі ТЗ. Перед реалізацією обов'язкова звірка з реальним асортиментом:
> власник надає перелік продуктів (Q2 — на старті наповнення програмне, без ERP) → карткове сортування з менеджерами продажів.

Правила формування категорій:
- Категорія існує, якщо містить **≥ 3 публічні продукти**; інакше зливається в ширшу. Жодних категорій «заради красивого меню».
- На головній — 4–8 категорій максимум.
- Продукт належить **одній канонічній категорії** (стабільний URL), але має **багато тегів задач** (для «Рішень» і фільтрів).

### Структура розділів

```
Головна
├── Каталог
│   ├── Детектори БПЛА
│   ├── РЕБ / придушення
│   ├── Антени
│   ├── Приймачі
│   ├── Комплекти
│   └── Аксесуари та живлення
├── Рішення
│   ├── Для піхоти
│   ├── Для автомобіля
│   ├── Для стаціонарного поста
│   ├── Для мобільної групи
│   ├── Для підрозділу (масштабна закупівля)
│   ├── Для спеціальних задач
│   └── Майстер підбору
├── Порівняння
├── Документація
├── Партнерам
├── Про компанію
├── Досвід застосування (V2 — розділ історій; у MVP відгуки живуть на сторінках продуктів)
└── Контакти
    (+ Заявка — глобальна дія з будь-якої сторінки, не окремий розділ меню)
```

### Навігаційна модель

**Header desktop:**
`Лого | Каталог ▾ | Рішення ▾ | Документація | Про компанію | Контакти  ||  🔍 Пошук | ⇄ Порівняння (лічильник) | [Отримати консультацію]`

**Header mobile:** `Лого | 🔍 | ☰`. Бургер відкриває drawer: категорії каталогу, рішення, решта розділів, унизу — телефон і месенджери.

**Footer:** дзеркало розділів + контакти з click-to-call + месенджери + юридичні дані + посилання на ключові документи.

Глобально доступні дії: пошук, порівняння (sticky-панель при непорожньому списку), заявка (кнопка/drawer).

## 9. Sitemap (маршрути)

| URL | Сторінка | Рендеринг | Індексація |
|---|---|---|---|
| `/` | Головна | SSG | так |
| `/catalog` | Весь каталог (огляд категорій + сітка) | SSG | так |
| `/catalog/[category]` | Категорія з фільтрами | SSG + клієнтські фільтри | так (чиста URL без параметрів) |
| `/products/[slug]` | Сторінка продукту | SSG | так |
| `/solutions` | Хаб рішень | SSG | так |
| `/solutions/[slug]` | Сторінка рішення | SSG | так |
| `/solutions/wizard` | Майстер підбору (V2) | інтерактивний острів | noindex |
| `/compare` | Порівняння | інтерактивний острів | noindex |
| `/docs` | Документація (хаб) | SSG | так |
| `/partners` | Партнерам: умови співпраці, форма звернення | SSG | так |
| `/cases` | Досвід застосування — історії (V2) | SSG | так |
| `/about` | Про компанію | SSG | так |
| `/contacts` | Контакти | SSG | так |
| `/request` | Заявка — fallback-сторінка (зазвичай drawer) | острів | noindex |

Правила URL:
- Лише читабельні стабільні slug латиницею: `/products/kozhan-4`, `/catalog/detectors`.
- Внутрішній `productId` живе тільки в backend і payload заявки — ніколи в публічних URL.
- Стан фільтрів — query-параметри (`?bands=1g,5g`); canonical завжди на чисту сторінку категорії.
- Зміна slug → обов'язковий 301-redirect (мапа редиректів зберігається в репозиторії).

## 10. Основні категорії

| Категорія | Що входить | Підпис на картці категорії | Специфічні фільтри |
|---|---|---|---|
| **Детектори БПЛА** | Портативні й бортові детектори активності БПЛА | «Виявлення активності БПЛА та каналів зв'язку» | діапазони, кількість діапазонів, тип антен, живлення, спосіб використання |
| **РЕБ / придушення** | Носимі, бортові, стаціонарні засоби протидії | «Придушення каналів управління та відео» | діапазони, спосіб розгортання, живлення (публікація параметрів — після безпекового ревью) |
| **Антени** | Виносні, спрямовані, бортові | «Розширення дальності та чутливості» | тип, діапазон, роз'єм, спосіб монтажу |
| **Приймачі** | Приймачі й аналізатори сигналів | «Прийом і аналіз сигналів» | діапазони, інтерфейси |
| **Комплекти** | Готові набори під сценарій | «Готові рішення під задачу» | сценарій, склад |
| **Аксесуари та живлення** | АКБ, кабелі, кріплення, кейси | «Живлення, монтаж, транспортування» | сумісність із продуктом, тип |

Картка категорії (на головній та в `/catalog`): зображення → назва → пояснення одним рядком → «N моделей →».

## 11. Модель «Рішення»

«Рішення» — це **курирована сторінка під сценарій використання**, а не автоматичний фільтр. Добірку складають продакт і менеджери продажів, бо рекомендація — це експертиза компанії, за яку вона відповідає.

### Модель даних

```
Solution {
  slug, title              // «Для автомобіля»
  audience                 // кому підходить (один рядок)
  scenario                 // 2–3 речення: умови застосування, типові загрози
  recommendations: [
    { productSlug,
      configurationPreset?,          // напр. «Версія для автомобіля»
      role: main | alternative | addon,
      reason }                       // «чому саме це» — одним реченням
  ]
  bundles: [productSlug]   // готові комплекти, якщо є
  faq: [{q, a}]            // 3–5 типових питань сценарію
}
```

### Структура сторінки рішення

```
Заголовок-сценарій («Обладнання для автомобіля»)
Для кого і в яких умовах (audience + scenario)
Рекомендований набір:
  ● Основний продукт    + «чому саме це»
  ○ Альтернатива        + «чим відрізняється»
  + Доповнення          (антени, живлення, кріплення)
Готові комплекти (якщо є)
FAQ сценарію (3–5 питань)
CTA: «Отримати консультацію під вашу задачу»
Посилання «Всі продукти для цього сценарію» → каталог із застосованим фільтром useCase
```

Зв'язок із продуктами: продукти мають теги `useCases[]` (`infantry`, `vehicle`, `stationary`, `mobile-group`, `unit`, `special`). Рекомендації — курировані; блок «усі продукти сценарію» — автоматичний за тегом.

**Майстер підбору** — інтерактивна надбудова над тими самими тегами: 3–4 кроки (Де? → Що потрібно? → Ключові вимоги?) → ранжований список рекомендацій. Логіка — у [04-logic.md](04-logic.md); реліз — V2 (у MVP — шість курированих сторінок).

## 12. User Flows (обов'язкові)

### Flow 1 — класична покупка: головна → категорія → продукт → заявка

```
Головна
 → клік «Детектори» (картка категорії)
 → /catalog/detectors: сітка, на картках 2–4 ключові параметри
 → [Детальніше] → /products/kozhan-4
 → above the fold: призначення, ключові ТТХ, ціна, наявність
 → (за потреби прокрутка: відгуки з фото/відео знімають останній сумнів)
 → [Залишити заявку] → drawer: продукт уже підставлений, 3 поля
 → успіх: номер заявки + «передзвонимо протягом робочого дня» + телефон менеджера
```
*Fallback:* не знайшов у категорії → пошук / фільтри / посилання «Не впевнені, що підходить? Підберемо під задачу» → «Рішення».

### Flow 2 — від задачі: головна → рішення → рекомендації → продукт → заявка

```
Головна → блок «Підбір за задачею»
 → плитка [Автомобіль] → /solutions/vehicle
 → рекомендації: основний / альтернатива / доповнення, кожне з «чому»
 → продукт: конфігурація «Версія для автомобіля» вже обрана (configurationPreset)
 → [Залишити заявку] → конфігурація підставлена в заявку автоматично
```
*Fallback:* сценарій нетиповий → майстер підбору (V2) → все одно не те → «Опишіть задачу» (та сама форма заявки з вільним коментарем).

### Flow 3 — пошук: запит → результати → фільтри → продукт

```
Будь-яка сторінка → пошук
 → введення «авто» → підказки групами: Рішення «Для автомобіля» · Продукти · Категорії
 → Enter → /catalog?q=авто: сітка результатів + фільтри для звуження
 → продукт
```
*Zero-result:* «Нічого не знайдено за “…”» + популярні категорії + «Опишіть, що шукаєте — підберемо» (заявка). Запит логується для поповнення синонімів.

### Flow 4 — порівняння: каталог → 3 продукти → порівняти → кращий

```
/catalog/detectors
 → чекбокс «Порівняти» на 3 картках
 → sticky-панель знизу: мініатюри + [Порівняти 3]
 → /compare: колонки, перемикач «Лише відмінності», відмінні значення підсвічені
 → вибір → [Детальніше] → /products/[slug] → заявка
```
*Обмеження:* продукт з іншої категорії → тост «Порівнюються продукти однієї категорії. Почати нове порівняння?».

### Flow 5 — конфігурація: продукт → зміна конфігурації → ціна → заявка

```
/products/kozhan-4
 → конфігуратор: Діапазони [4] · Антени (● Виносні) · Батарея (○ Посилена, +2 400 грн)
 → блок «Обрана конфігурація» живо оновлює ціну, наявність і людський підсумок
 → [Залишити заявку] → у payload: продукт + конфігурація + SKU варіанта
 → менеджер бачить у CRM продукт + людський опис конфігурації + SKU
```
*Fallback:* потрібної комбінації немає (disabled) → підказка «Недоступно з …» + «Уточнити у менеджера».
